## 一、需求总述

**一句话**：每天自动从聚水潭（erp321）抓取各渠道、各产品的**实发数量**与**实退数量**，
按自然周（周一~周日）汇总成 Excel，并生成一句话小结，推送到企业微信群。

**来源**：`聚水潭实发数量历史数据抓取.docx` / `聚水潭实退数量历史数据抓取.docx` 两份流程文档，
模板为 `每周各渠道实发_实退数据.xlsx`。

### 1.1 原始人工流程（工具要自动化的对象）

| 步骤 | 实发数量 | 实退数量 |
|---|---|---|
| 报表入口 | 报表 → **销售主题分析** | 报表 → **售后主题分析** |
| 时间筛选 | **发货时间** = 指定日期 | **进仓时间** = 指定日期 ⚠️ |
| 商品筛选 | 「包含商品」填该产品名下**全部商品编码**（逗号分隔） | 同左 |
| 生成 | 点「生成报表」 | 点「生成报表」 |
| 取数 | 「按渠道分析」页读各渠道的**实发数量** | 读各渠道的**实退数量** |
| 循环 | 按`分类编码`里**每个产品名称**各查一次（产品数由分类编码决定，当前 12 个） | 同左 |

> 「指定日期」默认 = **昨天**（脚本运行日的前一天，因聚水潭数据有 1 天延时）。

## 二、口径规则（最重要，出分歧时以此为准）

### 2.1 指标口径
- **实发数量**：实际发出的货，按**发货时间**归日。
  - ⚠️ 与「销售数量」不同：某天下单的货若次日才发，**实发算在发货那天**。
    （曾核对 7/22：销售数量=7 但实发=0，属正常，那几单在真正发货日被计入。）
- **实退数量**：售后退回，按**进仓时间**归日。
  - ⚠️ **2026-08-13 口径变更**：原按「登记时间」，现改为「**进仓时间**」（客户要求）。
    即只统计**实际退回入库**的，登记了但未进仓的不计入。
    实现：售后报表左上角「时间类型」下拉切到`搜进仓时间`，日期框字段由 `created` → `io_date`。
    实测对比（座椅套脚垫 7/1~8/12）：登记时间返回 3 行（含 2 行实退为空），进仓时间返回 1 行（淘宝=1），数据更干净。
- **净发货 = 总计发货 − 实退**（周表底部「实发数量」行 = `总计数量 − 实退数量`）。
- 其他列（销售单数、销售金额、毛利等）**一律不取**。

### 2.2 产品分类口径
- **唯一真相源 = 模板的`分类编码`sheet**（当前 12 个产品；可在可视化工具『产品分类』页或各脚本菜单里增删）。
- 一个「产品名称」下可能有多个「订货分类」和多个「商品编码」，
  查询时把该产品名下**所有编码**合并填入「包含商品」，得到的就是这个产品的合计。
  - 例：`奔腾小马` = `BTFSX01,BTFSX03,BTFSX02,BTFSX04,BTFSX05,BTFSX06`
  - 例：`熊猫扶手箱` = 熊猫灰(`20103183,20103185`) + 熊猫绿(`20103183g,20103185g`) 共 4 码
    → 8/10 = 抖4/拼3/淘3/红1 = **11**（经逐码验证无重复计数，用户已确认此口径）
- **增删产品或编码只改`分类编码`sheet，工具自动跟随**，无需改代码。
- 当前 11 个产品：熊猫扶手箱、三代马卡龙扶手箱、熊猫靠手、四代马卡龙扶手箱、糯玉米机械手刹、
  缤果扶手箱、座椅套脚垫、糯玉米电子手刹、奔腾小马、糯玉米靠手、缤果靠手。

### 2.3 渠道口径
- 4 个渠道：**抖音、拼多多、淘宝、小红书**（店铺后缀`劲风车生活`）。
- 报表「渠道」列形如`小红书-劲风车生活的店`，按**前缀匹配**归类。
- 同一渠道**多行要求和**（售后按「类型」拆成普通退货/仅退款/换货/补发等多行）。
- 汇总行`##`渠道为空，自动排除。
- 某渠道没出现在报表里 = **0**。

### 2.4 时间口径
- **周 = 周一 ~ 周日**（自然周）。
- **昨天** = 脚本运行日的前一天（数据有 1 天延时，故默认抓昨天）。
- **上周** = 本周一 − 7 天（即已结束的上一整周）。
- 日期筛选：把报表的起止日期**都填成目标那一天**（比点「昨天」下拉更通用，任意历史日/区间通吃）。

## 三、数据流与设计

```
聚水潭报表(bi.erp321.com)
   │  ① 直连URL打开报表 → 填日期+商品编码 → 点「生成报表」 → 读「按渠道」表格
   ▼
core/jst_report.py  ── 每次返回 {渠道: 数量}
   │  ② upsert（同 date+渠道+产品 覆盖对应指标）
   ▼
outputs/jst_master.csv   ★主数据 = 唯一真相源
   │  (date, channel, product, shipped, returned, crawled_at)
   │  ③ 渲染（任何时候都能从主数据重建表）
   ▼
outputs/每周各渠道实发_实退数据_YYYY年第WW周(MMDD-MMDD).xlsx
   │  ④ 推送
   ▼
企业微信群（文字小结 + Excel 附件）
```

**核心设计原则**：抓取只往**主数据**写；Excel 是主数据的**渲染产物**，可随时重建。
所以重复抓同一天不会污染，补抓历史周也能自然并入。

### 3.1 取数方式（重要背景）
- 聚水潭这套报表是老 **ASP.NET 报表引擎**，点「生成报表」后台返回的是**服务端渲染的 HTML 表格**，
  **没有明文 JSON 接口**（与另 4 个电商平台不同）。所以采用「驱动报表页 + 读结构化表格」。
- **直连报表 URL**（绕过 epaas 菜单）：菜单点开跨域 iframe 慢且不稳，直连约 8 秒即就绪。
  - 实发：`bi.erp321.com/app/daas/report/subject/adsorder/default.aspx`
  - 实退：`bi.erp321.com/app/daas/report/subject/adsaftersale/default.aspx`
- 关键元素：`filter.aspx`帧内 `order_date_begin/end`（日期）、`sku_id`（包含商品）、
  `DIV.btn_search`（生成报表按钮）；`channel.aspx`帧内是数据表格。
- **时间类型下拉**：不是 `<select>`，而是自定义下拉——`SPAN#date_desc` 显示当前项，
  选项是 `DIV.idtype`（搜登记时间/搜确认时间/搜订单发货时间/**搜进仓时间**/搜订单付款时间）。
  打开报表后由 `_ensure_date_type()` 自动切换，并**校验日期框 name 是否变成预期字段**（如 `io_date`），
  不符则直接报错，避免静默按错口径抓数。
- 按**表头文字**定位「渠道」「实发/实退数量」列 → 列顺序变化也不受影响。

### 3.2 稳定性设计（踩过的坑）
| 问题 | 解法 |
|---|---|
| 首屏自动加载会让第一组读到空 | 打开报表后 `_settle()` 等请求安静再查 |
| 生成时页面导航导致 `Execution context destroyed` | 所有 evaluate 包安全封装，整轮失败自动重试 1 次 |
| 判断「报表刷新完了没」 | 表格内容变化 + channel 重载 + 连续两次一致（稳定）才取值 |
| 两个报表互相干扰 | 各用**独立标签页**，用完即关 |
| 登录过期 | URL 被重定向到 `login.aspx` → **4 秒识别**并提示重登 |
| Excel 被占用写不进 | 另存 `..._请关闭原文件后替换_HHMMSS.xlsx` |
| **浏览器进程偶发崩溃**导致报表打不开 | `_open_with_retry`：打开失败**重试 3 次**（间隔 20s/60s/120s）；登录过期不重试 |
| **周一群里收到两份相同周表**（2026-08-17 发现） | 周一时「昨天(周日)所属的周」＝「上周」，抓取推送与周报推送指向同一份文件。<br>修复：`run_auto` 周一用 `crawl_dates(..., push=False)`，**只由周报推一次**。其余天照常由抓取推。 |

#### ★故障复盘：2026-08-17 发现「假 0」——查询偶发返回空表被当成真 0

- **怎么发现的**：用户要求核对「奔腾小马」实退。主数据 7/20~8/16 合计 6 套，ERP 实际 **13 套**。
  扩大排查：8/3~8/16 全产品实退 主数据 **60** vs ERP **114**，**缺 54 套（约 47%）**；
  8/12 全部 11 个产品在主数据里都是 0，而 ERP 有 15 套。
- **一开始的误判**：以为是「退货事后才入账，抓早了取不到」。
  **被实验推翻**：同一天 8/07 连查 3 次，结果 **16 → 0 → 16**——同一时刻同一条件，结果不一致，
  说明是**查询本身偶发返回假 0**，与数据入账时间无关。
- **根因**：点「生成报表」后，报表表格会**先清空、再填充**。
  旧逻辑「连续两次读到一致内容即认为渲染稳定」在**清空阶段**连读两次空表 → 判定为"新数据 = 0"。
  实退本来就常见 0，所以这种假 0 混在真 0 里**极难察觉**。
- **修复**（`jst_report._query_once`）：对「空结果」要求远比「非空」严格——
  - 非空：连续两次一致 + 已刷新 → 接受（约 1.5 秒）
  - **空：必须 channel 帧确实重载过，且连续 5 次、跨 ≥3 秒都读到空**，才认定这天真的没数据（约 4.1 秒）
  - 超时兜底只接受非空；`query()` 重试 3 次仍无可信结果则**抛错，而不是写 0**
    （旧代码返回全 0 会静默污染数据且看不出来）
- **验证**：8/07 连查 6 次恒 = 16；真空日 8/03、8/06 恒 = 0；有数/无数交替查询全部正确。
- **善后**：历史实退数据含假 0，已于 2026-08-17 全量重跑 7/20~8/16 回补。

#### 故障复盘：2026-08-13 早 9:00 定时任务没出数据
- **现象**：任务准时 9:00:02 触发，9:01:39 报「报表 filter 帧未就绪」后退出，无数据、未推群；
  但计划任务返回码为 0（进程正常结束），从任务状态看像"成功"，具有迷惑性。
- **实证**：Windows 应用程序日志显示同一时段 **python.exe 崩溃两次**
  （9:01:11、9:01:40，模块 `MSVCP140.dll`，异常码 `0xc0000005` 内存访问违规）。
  崩的是浏览器子进程 → 页面加载不出来 → 等满 90 秒超时。
  （排除：电脑连续开机 13 天、当天无休眠/唤醒事件；登录态正常，事后 4.2 秒即可打开报表。）
- **成因**：偶发资源冲突（当时机器上开着 20+ Chrome 进程），非配置或逻辑错误。
- **对策**：① 打开报表失败自动重试 3 次；② 计划任务启用**错过自动补跑**、不受电池限制、超时上限 2 小时。

### 3.2.1 异常报警（推企业微信群，叫人工处理）

抓取过程/抓完后自动检测三类问题，命中就**推群 + 桌面通知 + 记日志**（只提醒，不改数据）：

| 类型 | 判定 | 群里提示 |
|---|---|---|
| **登录超时** | 报表页被重定向到 `login.aspx`（约 4 秒识别） | 「登录已过期」+ 让人去重新登录再补抓 |
| **数据为空** | 当天 11 产品 × 4 渠道的**实发合计 = 0** | 「疑似没取到数据」+ 让人去核对该日 |
| **数据重复** | 当天全部数值与**前一天完全相同** | 「疑似报表未刷新/取到旧数据」 |

> 判空以**实发**为准：实退经常整天为 0 属正常，用实退判空会天天误报。
> 判重复比对的是「日期 × 4渠道 × 全部产品 × (实发,实退)」全部数值，全等才报——自然重合概率极低。
> 实现：`runner._check_data_anomaly()`，在 `crawl_dates` 抓完、渲染前调用，
> 因此**独立版和常开版都自动生效**。已验证：正常日不误报。

### 3.3 Excel 结构
- **实发数量 sheet**：A渠道(合并) × B日期(7天) × C~M 产品列(11个)；
  底部 `总计数量`(SUM) / `实退数量`(引用实退sheet) / `实发数量`(净=总计−实退)；
  再下方 `本周小结`（一句话小结）。**打开时默认停在此页。**
- **实退数量 sheet**：同样的网格 + 底部 `实退数量`(SUM)。
- **分类编码 sheet**：原样保留（是分类真相源）。
- 产品列**由分类编码动态生成**（全名），不再是模板里旧的 10 个简称列。

### 3.4 一句话小结
- 格式：`M.D-M.D主要产品净发货数据：{产品}{净发货}套，…（合计净发货N套）` + 实退同理一行。
- **累计逻辑**：数字始终对整周求和（未抓的天=0），故等于「周一~已抓最后一天」的累计。
  - 抓第1天 → `8.10…`；抓到第2天 → `8.10-8.11…`；…第7天 → `8.10-8.16…`（整周）
  - **每次抓取重建整表，自动覆盖前一天的小结。**
- 周一定时任务额外把**上周**周报另存 `周报_YYYY年第WW周(...).txt` 并推送。
- **群里推送的文字另有口径**（2026-08-21 改）：只发「本次抓的那几天」，不累计——19 号跑（抓 18 号）就只发 `8.18` 那天的数，一次抓多天则合并成一个区间 `8.1-8.9`。Excel 里的「本周小结」不受影响，仍是整周累计。周一那次抓取(周日)的单日文字由 `runner.push_crawled_note()` 单发（不带附件），周表仍只由周报推一次。

## 四、运行方式

| 入口 | 作用 |
|---|---|
| `一键安装.bat` | 装 Python/依赖/浏览器内核（幂等） |
| `登录.bat` | **有头**弹窗，人工登录一次，登录态持久保存 |
| `运行.bat` | 菜单：1抓昨天 / 2某天 / 3日期范围 / 4设定时 / 5取消定时 / 6出周报 / 7测试群推送 |
| `run.py --auto` | 定时任务入口：抓昨天；**周一额外出上周周报** |

- **抓取后台无头**（`headless: true`），不弹窗、无感知；
  运行记录 = 控制台进度（`[3/154]`）+ 桌面通知 + `logs\` 日志。
- **登录始终有头**（必须人工完成，脚本不代填密码）。
- 定时用 Windows 计划任务，任务名 `聚水潭爬虫_实发实退`。
  ⚠️ 设定时若填的时间**已过**，首次运行顺延到次日同一时间。
  任务设置已加固：**StartWhenAvailable（错过自动补跑）**、不受电池限制、超时上限 2 小时。

### 4.1 电脑关机 / 休眠时会怎样

工具运行在**本机**，需要「开机 → 计划任务触发 → 启动浏览器 → 抓数」。**电脑关机则不会运行。**

| 场景 | 结果 |
|---|---|
| 到点时电脑开着 | ✅ 准点自动跑 |
| 到点时关机/休眠，**当天晚些时候开机** | ✅ 开机后自动补跑（仍抓昨天，数据不丢） |
| 连续关机多天 | ⚠️ 开机后只补**最近一次**，中间遗漏的天需手动菜单 3 补抓 |
| 一直关机 | ❌ 不运行 |

> Windows 对错过的任务一般在开机后约 10 分钟内补跑一次。

**若需要"关机也能跑"**，须让它离开这台电脑：
1. **改休眠代替关机** + 任务勾选「唤醒计算机运行」（改动最小）；
2. 部署到一台**常开的机器/服务器**（整个文件夹拷过去装一遍即可，路径不写死、可移植）；
3. 云服务器（需处理登录态与无 GUI 环境，改造量较大）。

**自动补齐**：菜单 6 出某周周报时，若该周有天没抓过（且是已过去的天），**先自动补抓**再出报表；
菜单 3 抓跨周范围时，涉及的每一周各生成一张周表。

**只重跑某一个指标**（口径变更后回补历史用，避免白抓另一半）：
```python
# 例：实退口径从「登记时间」改为「进仓时间」后，重跑 7/20~8/12 的实退
from core import runner, calendar_utils as cal
dates = [d.isoformat() for d in cal.date_range(cal.parse_date('2026-07-20'), cal.parse_date('2026-08-12'))]
runner.crawl_dates(dates, push=False, metrics=('returned',))   # metrics=None 则两个都抓
```
`upsert` 是按指标合并写的，所以只重跑 `returned` **不会动已有的 `shipped` 数据**。
